## New Data Models

### `ChatHistory`

*   **Purpose**: Stores a historical record of user messages to the chatbot and the corresponding AI-generated responses. This is crucial for maintaining conversational context (if implemented in the future) and for auditing/debugging purposes.
*   **Attributes**:
    *   `id`: `UUID` (Primary Key). Unique identifier for each chat entry.
    *   `user_id`: `UUID` (Foreign Key, references `users.id`). Links the chat entry to the authenticated user. This ensures chat history is isolated per user.
    *   `message_content`: `String` (Text). The natural language input provided by the user.
    *   `response_content`: `String` (Text). The natural language response generated by the AI.
    *   `timestamp`: `DateTime` (with timezone, e.g., UTC). The exact time when the chat entry was recorded.
    *   `intent_classified`: `String` (e.g., max 50 chars). The primary intent identified by the LLM (e.g., "CREATE_TODO", "LIST_TODOS", "UPDATE_TODO", "DELETE_TODO", "UNKNOWN", "GREETING").
    *   `extracted_entities`: `JSONB` (or equivalent for FastAPI/SQLModel). A JSON object containing structured data extracted by the LLM from the user's message (e.g., `{"title": "Buy milk", "due_date": "2026-07-01", "status": "completed"}`). This field stores the parsed parameters for todo operations.
*   **Relationships**:
    *   Many-to-one with `User` model: A `User` can have many `ChatHistory` entries.
*   **ORM Integration (SQLModel)**:
    *   Will be defined in `backend/app/db/models/chat.py` and `backend/app/models/chat.py`.
    *   A corresponding Alembic migration will be needed to create the `chat_history` table.

## Existing Data Models (Referenced, Not Modified)

### `User` (from Phase I)

*   **Purpose**: Stores user authentication and profile information.
*   **Reference**: `chat_history.user_id` will link to `users.id`.

### `Todo` (from Phase II)

*   **Purpose**: Stores individual todo items for each user.
*   **Modification Status**: Will be directly interacted with by the backend logic after AI parsing, but the `Todo` model itself will not be modified for Phase III. All CRUD operations will use existing `Todo` service logic.
